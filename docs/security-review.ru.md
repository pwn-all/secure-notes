# Проверка безопасности SecNote и соответствия OWASP

Проверка проведена 2 октября 2026 года. Изучены backend на Rust и Axum, клиентский JavaScript, PoW worker, service worker, HTML, конфигурация, Dockerfile, установочные скрипты и GitHub Actions. В код внесены исправления подтверждённых проблем и добавлены регрессионные проверки. Архитектура подходит для обмена одноразовыми зашифрованными заметками при доверенном клиенте, но исходная реализация содержала ошибки доверия, защиты ответов и обработки размера заметок.

Основа оценки — [OWASP Top 10 2025](https://top10.owasp.org/2025/) и стабильная версия [OWASP ASVS 5.0.0](https://github.com/OWASP/ASVS/releases/tag/v5.0.0). Top 10 описывает основные классы рисков; ASVS задаёт требования для проверок. Работа включает анализ исходников, регрессии, запуск release-бинарника через настоящий локальный TLS/HTTP2 и проверку UI в Chromium 149. Она не подтверждает выполнение всех требований ASVS или конкретного уровня L1, L2 либо L3. Производственная инфраструктура, настройки GitHub, публичный TLS endpoint и настоящий Docker runtime на Linux не проверялись.

## Итог финальной проверки и условия публикации

Финальные проверки текущего кода прошли: 27 Rust-тестов, 24 Node-теста, release build, Clippy, форматирование, RustSec, интеграционные запросы через HTTPS/HTTP2 и пользовательский сценарий в Chromium. В рассмотренном коде после исправлений не найдено подтверждённых блокирующих уязвимостей в рамках описанной модели доверия. Код подготовлен к выпуску.

Готовность конкретного production-развёртывания пока условная. До открытия публичного доступа необходимо:

1. Собрать и запустить точный Docker-образ на Linux, если выбран Docker, проверить UID/GID 65532, минимальные capabilities, `no_new_privs`, чтение заметки и обновление TLS. Здесь проверены ветки entrypoint через shell harness; фактическую смену Linux credentials/capabilities он не проверяет.
2. Задать уникальный постоянный `SIGNING_KEY`, корректный `PUBLIC_HOST`, действующий сертификат и закрытый доступ к секретам. Проверить публичную цепочку TLS, redirect и security headers.
3. Настроить продление сертификата с вызовом `docker exec --user 0 secnote /app/entrypoint.sh --reload-tls`, либо SIGHUP для сервера с прямым доступом к обновлённым файлам. Успех подтвердить сообщением backend о reload и новым сертификатом снаружи. Встроенного расписания ACME renewal нет.
4. Установить ingress limits на общее число соединений, начальные байты, idle sockets и суммарную частоту запросов. При использовании reverse proxy определить доверенные proxy и проверить фактическое действие IP rate limits.
5. Выпускать backend и frontend совместно, со всеми новыми файлами, включая `Cargo.lock`, `.env.example` и тесты. Проверить успешный CI на публикуемом commit. Без backend v2 новый frontend API не примет.

Эти условия относятся к проверке окружения и эксплуатации. Без их подтверждения безусловное заключение «production готов» было бы шире выполненного аудита.

## Архитектура и границы доверия

Клиент генерирует случайный AES-ключ длиной 32 байта и IV длиной 12 байт через WebCrypto. Текст шифруется AES-256-GCM с 16-байтовым тегом. Сервер получает base64url от `IV || ciphertext || tag`, TTL и токен `SHA-256(AES key)`. Сам AES-ключ помещается в fragment ссылки, который браузер не включает в HTTP-запрос.

Backend хранит ciphertext, хеш токена чтения и срок жизни. Для создания и чтения требуются одноразовые PoW challenges, привязанные к IP и типу операции. Создание связывает PoW с TTL и blob, чтение — с ID заметки. При чтении сервер сначала проверяет PoW, затем сравнивает хеш токена за постоянное время и под блокировкой удаляет заметку. Одинаковый ответ 410 при отсутствии заметки и неверном токене уменьшает раскрытие её существования.

На сервере нет БД, запросов SQL, интерпретации содержимого заметок или исходящих HTTP-запросов по пользовательским URL. Клиент показывает расшифрованный текст через `textarea.value`. HTML переводов проходит через ограниченный список тегов с удалением атрибутов. Настройка внешнего API относится к клиентским запросам браузера и сама по себе не создаёт серверный SSRF.

Ссылку следует считать секретом доступа: любой обладатель полной ссылки может прочитать заметку. Подпись API требует отдельно доверенного открытого ключа. Без доверенного исходного JavaScript злоумышленник, контролирующий доставку страницы, способен получить ключ и plaintext до шифрования или после расшифрования.

## Подтверждённые проблемы и исправления

### Подпись ответа не обеспечивала свежесть и контекст

**Приоритет высокий для заявленной защиты от перехвата TLS.** Исходная Ed25519-подпись покрывала только тело ответа. Клиент принимал ранее подписанное тело без доказательства, что оно относится к текущему запросу. Метод, URL и HTTP-статус также не проверялись криптографически. Перехватчик мог повторить старый ответ или изменить его контекст; для эксплуатации нужен контроль транспорта при сохранении доверенного клиентского кода.

В `src/lib.rs` добавлена подпись `x-secnote-sig-v2`. Она покрывает идентификатор протокола, HTTP-метод, точный path и query, случайный идентификатор обращения, SHA-256 фактически полученного тела запроса, статус ответа и его исходные байты. В `website/app.js` каждый запрос получает новый 128-битный nonce; проверка использует собственный контекст клиента и выполняется до декодирования JSON. Это также обнаруживает изменение тела запроса на пути к серверу при проверке последующего ответа.

Старый заголовок `x-secnote-sig` оставлен для совместимости внешних API-клиентов. Официальный frontend требует v2 и не принимает старую подпись как замену. Внешним клиентам необходимо внедрить v2 и свежий nonce. Старые клиенты сохраняют исходный риск повторного воспроизведения. Изменение запроса обнаруживается после обработки сервером: подпись ответа не предотвращает уже совершённые побочные эффекты и не шифрует запрос.

Rust-тест проверяет отказ при изменении каждого поля и тела ответа. Общий Ed25519-вектор подтверждает совместимость server middleware с клиентской проверкой. JS-тест проверяет, что старый корректно подписанный ответ отвергается для нового обращения.

### Допустимая заметка могла исчезнуть без расшифрования

**Приоритет высокий по целостности и доступности данных.** Backend принимал plaintext до 32768 байт, но `decrypt()` ограничивал encoded blob теми же 32768 символами. После добавления IV, тега и base64url максимальная заметка занимает 43728 символов. Сервер уже удалял её, прежде чем frontend выдавал ошибку размера. Проблема возникала для текста больше 24548 байт при исходных лимитах.

Клиентский предел blob исправлен на 49152 символа. Backend ограничивает поддерживаемую конфигурацию plaintext до 32768 байт и encoded blob до 49152 байт. Клиент учитывает оба объявленных сервером предела при вычислении доступного размера текста. Исправлены устаревшие значения в README. JS-тесты проверяют полный цикл для максимального ASCII-текста и многобайтового UTF-8, а также отказ при изменении ciphertext и неверном AES-ключе.

### Доверенный ключ мог игнорировать явный pin или сбрасываться

**Приоритет средний.** В `showApiConfirmModal()` ранее доверенная запись для API проверялась раньше pin из новой ссылки. Если endpoint отвечал прежним ключом, функция принимала его без соблюдения нового pin. Кроме того, сохранение настроек собственного origin без нового ключа сбрасывало текущий ключ; следующий `/info` мог запустить новое автоматическое доверие.

Явный pin теперь имеет приоритет, а сохранение собственного API URL сохраняет ранее доверенный ключ. При смене origin ключ берётся из его собственной записи доверия. Pin проверяется при каждой соответствующей навигации; некорректные URL и ключи в ссылке останавливают обработку. Хранилище доверия устойчиво к JSON неправильной формы, а base64url-декодер отвергает неканоническое представление.

Регрессионные тесты воспроизводят конфликт stored key и pin, сохранение настроек того же origin, конфликт двух явных pin и ручную замену ключа уже подтверждённого внешнего API.

### Ограничение числа заметок допускало большой расход RAM

**Приоритет средний, эксплуатация требует создания заметок с PoW.** Исходный предел 50000 заметок при blob до 49152 байт допускал около 2,29 GiB только encoded ciphertext. Дополнительно выделяются таблицы, challenges, JSON, TLS и сетевые буферы. Каждый `/info` обходил все хранилища; операции создания и выдачи challenges также делали полный проход очистки при каждом запросе.

Добавлен общий бюджет `MAX_NOTE_STORAGE_BYTES`, по умолчанию 64 MiB, с учётом объёма под той же блокировкой, что и вставка/удаление. Чтение и очистка истёкших записей освобождают бюджет. Статистика использует счётчики и размеры таблиц вместо обхода каждой записи. Обязательная периодическая очистка сохранена; дополнительная очистка на вставке выполняется при достижении предела.

`MAX_CONCURRENT_API_REQUESTS`, по умолчанию 64, ограничивает работу API до чтения тела и выделения буферов. Тело ограничивается до JSON parsing и читается не более 10 секунд; обработчик также имеет отдельный предел 10 секунд. Перегрузка получает 503 с `Retry-After`. Тесты проверяют исчерпание бюджета, его освобождение, восстановление после перегрузки и отказ от слишком большого JSON.

Это предел encoded ciphertext, а не гарантия максимального RSS процесса. В финальной проверке также добавлены ограничения HTTP-заголовков, описанные ниже. Ограничения общего числа соединений и общий сетевой rate limit остаются задачей ingress и окружения.

### Service worker сохранял идентификаторы заметок

**Приоритет средний по приватности метаданных.** Service worker сохранял любые успешные GET-ответы своего origin вне API. Страница `/?p=<nid>&pin=<key>` попадала в CacheStorage под полным URL. Fragment с AES-ключом в HTTP request не передавался, но ID заметки и история обращений могли оставаться на диске браузера.

Кеш теперь ограничен публичными статическими путями. Получение и сохранение shell используют URL без query, чтобы исключить метаданные и из ключа кеша, и из URL кешируемого сетевого ответа. API и произвольные пути обходят кеш. Версия кеша повышена до `secnote-v4`; при активации удаляются только старые кеши SecNote. JS-тест проверяет сохранение канонического `/` и обход API и посторонних путей.

### Закрытие заметки оставляло plaintext в DOM

**Приоритет средний для локального доступа к открытому браузеру.** Кнопка закрытия только скрывала экран. Расшифрованный текст оставался в скрытом `textarea`, а ссылка с AES-ключом сохранялась в адресе после чтения. Текст отправителя также оставался в скрытом поле после создания заметки.

При закрытии plaintext очищается из DOM. После успешного чтения удаляются текущая ссылка на ключ в состоянии JS и fragment текущей записи истории. После отправки очищается compose input, а сброс формы очищает старую ссылку и QR. Проверка подтверждает очистку поля чтения и текущего ключа.

Очистка DOM и ссылок на строки не гарантирует физическое затирание памяти JavaScript. Предыдущие записи истории, clipboard, расширения, снимки памяти и копии получателя остаются вне этой меры.

### Сборка и CI не фиксировали проверяемое состояние

**Приоритет средний для цепочки поставки.** `Cargo.lock` отсутствовал среди отслеживаемых файлов и игнорировался правилом `*.lock`; при этом Dockerfile пытался его копировать. Новая сборка могла разрешить другие зависимости либо не собраться из свежего checkout. CI не проверял frontend и RustSec. Actions использовали изменяемые version tags, а job, запускающий код PR, имел `issues: write`.

Существующий локальный lockfile добавлен в набор файлов для коммита, исключение в `.gitignore` исправлено, Docker и CI используют `--locked`. В CI добавлены frontend/deployment regressions, HTTPS runtime smoke, форматирование, проверка всех targets Clippy и RustSec с отказом при предупреждениях. Audit выполняется также еженедельно. Публикация Pages зависит от отдельного validation job с release build и runtime smoke; права публикации получает только deployment job. Используемые actions закреплены по commit SHA, полученным из официальных репозиториев; credential persistence в checkout отключён. Право `issues: write` перенесено в отдельный job сообщения о сбое, который не запускает код PR. `.dockerignore` исключает секретные env-файлы, TLS-ключи и служебные каталоги из build context; `.gitignore` исключает также `.env.*`, сохраняя шаблон `.env.example`.

Состояние branch protection, обязательность проверок и repository permissions не доступны из локальных файлов. Автоматическое слияние Dependabot должно быть защищено обязательными успешными проверками и политикой репозитория.

### Bootstrap и локальная конфигурация расходились с документацией

**Приоритет низкий.** `.env.example` отсутствовал, хотя README и `1click.sh` требовали его. `app-config.js` не подключался в HTML. Установочный скрипт обновлял `.env` через неэкранированный sed replacement и мог оставить слишком широкие права или резервную копию файла с секретом.

Добавлен шаблон `.env`, подключён runtime config, исправлена запись переменных через приватный временный файл с правами 0600. Скрипт отвергает symlink для `.env`, проверяет hostname и задаёт `PUBLIC_HOST`. Docker setup также задаёт фиксированный hostname при автоматическом получении сертификата. Установочный тест проверяет первый запуск, сохранение существующей переменной, специальные символы в пути и отказ для symlink.

В HTML добавлены `no-referrer` и ограничительная CSP для статического хостинга. При обслуживании Rust backend HTTP CSP действует совместно с ней и остаётся более строгой. Meta CSP не заменяет HTTP `frame-ancestors`, HSTS и X-Frame-Options на отдельном статическом хостинге; их должен настроить этот хостинг. Chromium подтвердил PoW worker, QR, подписи и внешний HTTPS API без неожиданных ошибок CSP. File mode и Tor Browser отдельно не проверялись.

### Смена API во время запроса могла изменить результат операции

**Приоритет средний.** Отправка проверяла текущий API после подготовки PoW, но после сетевого запроса могла использовать уже изменённый API для построения ссылки. В результате ссылка на заметку прежнего сервера могла указывать на новый origin. При чтении ответ также мог попасть в уже изменившееся состояние экрана. Кроме того, обновление статуса могло снова включить кнопку отправки во время выполнения операции.

Добавлены признаки выполняемой операции, отказ от повторных нажатий и проверка контекста после получения ответа. Чтение использует снимок ID, AES-ключа и API, а затем проверяет актуальность перед выводом текста. Изменение signing key также инвалидирует PoW context. Проверка актуальности добавлена и в необязательный WebMCP create tool. JS-регрессия подтверждает блокировку повторного нажатия и отсутствие ссылки на новый API при получении старого ответа.

Финальная проверка выявила отдельную гонку навигации: предыдущий запрос `/info` и обработчики старого trust dialog могли продолжить работу после перехода к новой ссылке. Добавлен общий `AbortController` для конфигурации API и навигации; отмена закрывает старый dialog, удаляет обработчики и таймер фокуса и запрещает сохранение его ключа. Fetch учитывает внешнюю отмену и во время чтения тела. Навигация сразу очищает plaintext, старые ссылки и QR, а устаревший PoW init не меняет лимиты нового контекста. Регрессии воспроизводят медленный ответ прежней навигации, отменённый dialog и поздний click; все проходят.

### HTTP deadline не действовал без таймера

**Приоритет средний по доступности.** API body deadline не покрывает чтение заголовков. HTTP/1 builder Hyper использовал deadline, который не активен без установленного timer. Теперь для HTTP и HTTPS явно подключён `TokioTimer`: полные заголовки читаются не более 10 секунд, receive buffer ограничен 32 KiB, количество полей — 64. HTTP/2 ограничен 64 параллельными streams, header list 16 KiB и send buffer 64 KiB; настроены keepalive interval 30 секунд и timeout 10 секунд.

Rust-регрессия использует настоящий Hyper поверх duplex stream. Отдельная runtime-проверка отправляет неполные HTTP/1 заголовки через TLS socket и подтверждает закрытие в пределах deadline. HTTP/2-проверка подтверждает опубликованные SETTINGS и подписанный ответ `/info`. Стадия auto-protocol detection, полностью idle socket и незавершённый HTTP/2 preface остаются за пределами HTTP/1 deadline; для них нужны ingress limits.

### Root runtime и обновление сертификата требовали исправления

**Приоритет средний для production deployment.** Ранее certbot и сервер выполнялись под root; обновление файлов сертификата не меняло активную TLS-конфигурацию без перезапуска, который уничтожает заметки.

В Docker entrypoint root используется для получения сертификата и подготовки приватных копий. После этого `setpriv` запускает сервер с UID/GID 65532, без supplementary groups, с `no_new_privs`. Для низких портов сохраняется только `NET_BIND_SERVICE`; для высоких портов capabilities удаляются. Ошибка снижения привилегий останавливает startup. Runtime TLS directory имеет 0750, файлы — 0640 с root owner и группой сервера. Explicit nonroot startup использует уже доступные ему certificate paths и не повышает права.

На Unix backend обрабатывает SIGHUP: новая TLS-конфигурация заменяет активную только после успешной загрузки пары certificate/key. Ошибка сохраняет предыдущую конфигурацию. Docker hook `--reload-tls` сначала подготавливает оба файла, переносит их в runtime directory и отправляет HUP работающему PID 1. Успех запроса сигнала не равен успешному reload: следует проверять backend log и внешний сертификат. Runtime-проверка подтверждает настоящий TLS reload без потери заметки и отказ от некорректного ключа. Shell harness проверяет копирование, права файлов, параметры `setpriv`, обе ветки портов, nonroot startup, refresh и отказ startup при ошибке снижения прав. Настоящий Linux Docker runtime и расписание renewal остаются условиями deployment.

| Категория | Результат проверки |
| --- | --- |
| A01 Broken Access Control | Непредсказуемый 128-битный ID и отдельный 256-битный токен доступа; сравнение хешей за постоянное время; неверный токен не уничтожает заметку. Исправлена обработка pin. Возможность читать заметку определяется владением полной ссылкой. |
| A02 Security Misconfiguration | Есть HTTPS, CSP, HSTS, nosniff, no-referrer и запрет framing на backend. Исправлены local config, setup и CI permissions; Docker entrypoint снижает права сервера. Для deployment обязательны фиксированный PUBLIC_HOST, стабильный signing seed, приватные сертификаты и проверка Linux runtime. |
| A03 Software Supply Chain Failures | Исправлены lockfile, locked builds, SHA actions и Docker context; добавлены автоматический audit и validation gate для Pages. RustSec на проверенном наборе зависимостей не нашёл известных проблем. Образы Docker остаются закреплены по tags, а не digest; minified QR library требует собственного контроля происхождения. |
| A04 Cryptographic Failures | AES-256-GCM, случайные ключи/IV, WebCrypto и Ed25519 соответствуют выбранной модели. Исправлены размер blob и подпись контекста. TOFU и доставка JS ограничивают гарантии. SHA-256 применяется к случайному ключу, а не к пользовательскому паролю; password KDF здесь не требуется. |
| A05 Injection | Подтверждённых SQL/command injection в обработке API не найдено. Plaintext выводится как значение поля, переводы очищаются, внешние адреса ограничены HTTPS/loopback. Исправлена небезопасная подстановка путей в setup. Полного browser fuzzing HTML sanitizer не было. |
| A06 Insecure Design | Есть PoW, разделение create/view, expiry, rate limits, лимиты таблиц и атомарное чтение. Добавлены бюджет ciphertext и ограничение параллелизма. Недоставка после удаления и действия обладателя ссылки остаются свойствами протокола. |
| A07 Authentication Failures | Пользовательских аккаунтов и cookie sessions нет; доступ основан на secret capability. Исправлены pin и сохранение доверия. Первое unpinned подключение всё ещё зависит от TLS и доверенного клиента. |
| A08 Software or Data Integrity Failures | GCM обнаруживает изменение ciphertext. V2 подпись связывает ответы с запросом и свежим nonce; frontend не допускает downgrade к старой подписи. Компрометация сервера доставки JS или устаревший сторонний клиент остаются отдельными рисками. |
| A09 Security Logging and Alerting Failures | Startup logs не включают AES-ключи или signing seed. Backend не содержит развитых security counters и alerting. Отказы, rate limiting, bans и перегрузка нуждаются в агрегированном мониторинге с учётом приватности. Это остаётся пробелом. |
| A10 Mishandling of Exceptional Conditions | Есть типизированные ошибки, ограничения JSON и Retry-After. Добавлены API/HTTP deadlines, HTTP/2 limits и корректная ошибка вместо пустого тела при сбое подписи. Некорректный TLS reload сохраняет работающую конфигурацию. Проверены неполные HTTP/1 заголовки через TLS; масштабная нагрузка, initial/idle sockets и все обрывы транспорта не покрыты. |

Проверенные области ASVS: frontend и HTTP-защита, API validation, capability access, cryptography, key trust, конфигурация и обработка ошибок. Требования к password login и пользовательским сессиям неприменимы к текущему продукту. Организационные требования, полный контроль deployment и безопасность операционной системы не оценены.

## Ограничения и оставшиеся задачи

1. **Доставка клиента и первый ключ.** Для защиты от злоумышленника с доверенным TLS-сертификатом нужна отдельно доверенная копия frontend и проверенный через независимый канал Ed25519 pubkey. Pin в ссылке с того же недоверенного канала не создаёт независимого доверия. Это ограничение архитектуры, а не свойство, которое исправляет подпись ответа.

2. **Удаление до доставки.** Заметка исчезает после успешной авторизации API чтения, до подтверждения получения и расшифрования браузером. Обрыв соединения или закрытие страницы могут потерять заметку. Резервирование и подтверждение чтения требуют изменения протокола, сроков хранения и обработки повторных попыток.

3. **Linux deployment и сертификаты.** Сервер в Docker теперь запускается под UID/GID 65532 после root setup; live TLS reload реализован и проверен в локальном бинарнике. Фактические Linux permissions/capabilities требуют проверки точного контейнерного образа. Планировщик renewal не добавлен; необходимо настроить ACME-процесс и reload hook. Standalone certbot требует свободного порта 80: для renewal одновременно с приложением нужен подходящий способ challenge validation.

4. **DoS на уровне сети.** Добавлены API limits, HTTP/1 header deadline и HTTP/2 ограничения. Они не ограничивают общее число соединений, полностью idle sockets и стадию начального определения протокола. Нужны ingress limits и нагрузочное тестирование. Behind-proxy deployment видит IP прокси через ConnectInfo; нельзя просто начать доверять X-Forwarded-For от всех клиентов. Требуется явная политика доверенных прокси.

5. **RAM и физическое удаление.** Удаление записи из HashMap прекращает её доступность через API. Оно не доказывает затирание всех allocator buffers, swap, core dumps или VM snapshots. Истёкшие записи физически удаляются периодически, по умолчанию раз в 30 секунд; логический доступ к ним блокируется сразу по expiry.

6. **Приватность инфраструктуры.** Backend временно получает IP и сохраняет его salted hash. CORS `*` намеренно позволяет независимый frontend, включая file origin: cookie authentication и credentialed CORS отсутствуют, токен чтения передаётся явно. Это не даёт разрешения на чтение без токена. Внешний API получает read token и ciphertext, а сообщения с полной ссылкой могут быть доступны провайдеру используемого канала. Логи reverse proxy могут содержать `?p=`, даже при отсутствии fragment; политику retention следует определять по реальному deployment.

7. **Мониторинг и воспроизводимость deployment.** Добавить агрегированные счётчики bans, PoW failures, отказов по вместимости и latency, без raw IP, note IDs, tokens, ключей и содержимого. Проверить required CI checks для auto-merge, digest контейнерных образов и воспроизводимый источник QR library. Состояние этих внешних систем не подтверждено локальным аудитом.

## Выполненные проверки

Все 18 исходных Rust-тестов прошли до изменений. После финальных исправлений прошли 27 Rust-тестов (24 library и 3 binary) и 24 Node-теста (17 frontend/setup и 7 deployment). В них проверяются существующие race conditions одноразового чтения/challenge, неверные токены и PoW, expiry и bans, а также подписи, размеры, trust store, кеш, RAM budget, setup, redirect, HTTP timer и смена API/навигации во время операции.

Также прошли release build с `--locked --offline`, `cargo fmt --check`, `cargo clippy --locked --offline --all-targets -- -D warnings`, `git diff --check`, JavaScript syntax checks, `bash -n` и разбор YAML workflow через Ruby. `tests/runtime-smoke.cjs` проверил release-бинарник по сети через локальный HTTPS с проверкой собственной test CA: security headers, фиксированный redirect, CORS, HTTP/2 SETTINGS, Ed25519 v2, заметку 32768 UTF-8 байт, неверный токен без удаления, однократное чтение, signed 410, valid/invalid TLS reload и настоящий header deadline.

Chromium `149.0.7827.55` на последней release-сборке подтвердил создание/расшифрование максимальной Unicode-заметки, PoW worker, QR под CSP, внешний API с pin и реальным CORS/preflight, одноразовое чтение, очистку URL fragment/DOM и канонические CacheStorage URLs. AES-ключи отсутствовали во всех наблюдённых API requests. Неожиданных browser/CSP errors — 0. Итог сохранён в [browser-smoke.json](browser-smoke.json). Браузерный harness разрешал локальный self-signed сертификат; публичную TLS chain он не проверяет. Firefox, Safari, Tor, file mode, Docker build/run на Linux, GitHub Actions run и публичный production endpoint не запускались.

Проверка `cargo-audit 0.22.2` выполнена с `--deny warnings`, включая отозванные версии. Для 152 записей зависимостей инструмент сообщил 0 известных уязвимостей и 0 предупреждений. Использована публичная база RustSec с 1279 advisory entries, commit `6de4455103aced2cba86e3b86e5c090b22827cf1`, от 2 октября 2026 года, 00:25 по времени Дубая. Этот результат относится к текущему `Cargo.lock` и состоянию базы, а не гарантирует отсутствие неизвестных уязвимостей. Машинный результат сохранён рядом в `dependency-audit.json`.

Команды для повторной проверки:

```bash
cargo test --locked
node --test tests/*.test.cjs
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo audit --deny warnings
cargo build --release --locked
node tests/runtime-smoke.cjs --binary target/release/secure_notes
```

Backend и официальный frontend следует обновлять вместе: новый клиент требует signature v2 и отвергает старый backend. Новый backend сохраняет legacy body signature для существующих интеграций, но такие клиенты должны перейти на v2. Перезапуск очищает заметки; без стабильного `SIGNING_KEY` он также меняет ключ API.
